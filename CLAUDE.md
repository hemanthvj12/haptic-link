# HapticLink: notes for Claude

HapticLink for DualSense gives games a virtual wired DualSense fed by a real one on Bluetooth, so haptics, adaptive triggers, rumble and lights work. PeripheralHub (the owner's battery tray app, github.com/hemanthvj12/peripheral-hub) works with it through its control pipe (see "With PeripheralHub"). The README covers usage and the pipe protocol; this file holds the facts behind it.

## Layout
- `drivers/HapticLink.Pad`: UMDF2 HID minidriver in C (own port of Microsoft's vhidmini2, MS-PL sample, not copied) with punktfunk's DualSense descriptor and feature blobs (MIT OR Apache-2.0). Hardware id `HapticLink_DualSense`, UMDF 2.15, `ProcessSharingDisabled`, INF decorated `NTamd64.10.0...19041` (infverif rejects `[*.Filters]` below 18362). A 2 ms→4 ms high-resolution timer thread completes one READ_REPORT per tick. Shared memory `Global\HapticLinkPad0`, layout in `PadShared.h` = `VirtualPad` in the service (a test checks both agree; magic "HLP1"). Pairing MAC is our own so SDL/Steam don't merge it with another virtual pad.
- `drivers/HapticLink.PadHost`: C DLL wrapping `SwDeviceCreate` (`PhPadCreate`/`PhPadClose`). **From .NET JIT code `SwDeviceCreate` fails with 0x8007007E for every input: the callback must be in an image on disk**; the same call from C works. Needs admin; two creations with the same instance → 0x800700B7.
- Driver build: normal MSVC toolset (`$(DefaultPlatformToolset)`) + the `Microsoft.Windows.WDK.x64` NuGet's UMDF headers/stub lib unpacked into `artifacts\wdk` (no WDK install); needs `ntdll.lib` (stub calls `DbgPrintEx`) and `WIN32_NO_STATUS` before `windows.h`. Inf2Cat from the same NuGet. `drivers/build-service.ps1` builds driver + helper + service into `artifacts\service` (signs with a dev certificate unless `-PfxPath`).
- `src/HapticLink.Service` (LocalSystem service `HapticLink`, installed to `%ProgramFiles%\HapticLink\Service`, admins-only ACL; log `%ProgramData%\HapticLink\service.log`). Modes `service`, `console`, `setup`, `remove`. Its `<Version>` is the service's own: the app re-runs setup (one UAC prompt) only when the bundled service is newer, so bump it when the service, driver or helper change.
  - **Memory (measured 2026-11-06, Task Manager, bridging with haptics):** ~10 MB without game sound, ~13 MB with the controller speaker playing (was ~30 MB). The garbage made hundreds of times a second is what grew it: the pad was read and written through a `FileStream` on its overlapped handle (allocations per report) and the rumble pump made a new delegate 1,000 times a second, and the GC's first budget is sized from the CPU cache (~18 MB) and it keeps memory it once grabbed. `PadConnection` now uses `ReadFile`/`WriteFile` with one reused native OVERLAPPED per direction (event low bit set so nothing goes to a completion port; `Dispose` cancels the pending read with `CancelIoEx`), the pump's delegate is made once, and the loop calls `GC.Collect()` whenever 1 MB was allocated since the last one or every 30 s (with the speaker playing, Concentus's Opus encoder makes ~0.4 MB/s: a collection every ~2–3 s; at 2 MB it was ~13 MB with haptics timing unchanged: 6–9 late, 0 dropped per 30 s, write 1.2 ms; 1 MB not measured yet). ReadyToRun made no difference. **Keep hot loops allocation-free.** **Still to do for the owner's 10 MB target (2026-11-07; the speaker case is ~13 MB), estimates, best value first:** (1) the speaker's garbage: `Speaker.Encode` makes a new 200-byte frame per block (a small pool or a reused buffer per queued block would do) and Concentus allocates inside `Encode`: a native libopus (`opus.dll`, BSD, shipped next to the service and loaded by full path, never from PATH, since the service runs as SYSTEM) would remove that, ~2–3 MB while the speaker plays, and use less CPU; (3) fewer threads (~20–30 now, ~1–2 MB, careful with haptics timing); (4) Native AOT for the service (~3–5 MB in every state; ~20 `[ComImport]` interfaces in Audio.cs, ComObjects.cs, HapticsRelay.cs → `[GeneratedComInterface]`, full in-game retest). Floor with everything: ~5–7 MB. Testing helpers: a WASAPI test tone into the speaker endpoint at level 0.002 (inaudible, still above the speaker's -66 dB threshold) drives both the haptics and the Opus path without a game.
  - Loop (1 s): switch off → stop; no bridge → find the first Bluetooth DualSense/Edge (`PadConnection.FindBluetoothPads`) and `Bridge.Start`; a dead bridge (no report for 4 s) is released; failures retry after 15 s. The switch is `HKLM\SOFTWARE\HapticLink\Enabled` (missing = on); `Speaker` (missing = on) is the controller speaker switch, applied to the running bridge every second (`Bridge.ApplyFeatures` → `HapticsRelay.SpeakerOn`).
  - `Bridge`: reads features 0x05/0x20 (refuses to start if they fail: a half-asleep pad), creates the section (DACL SY, BA, LS for WUDFHost), hides the real pad with HidHide (cloak on, `--dev-hide`, allowed apps = service exe + registered readers; only undoes what it changed; `session-undo.txt` written first and replayed at the next start after a crash), creates the device (enumerator `VID_054C&PID_0CE6&MI_03`, instance `HLINK_PAD_0`, container `484c4e4b-…`), sends the light-bar release, pumps output, shows the speaker and starts `HapticsRelay`.
  - `setup`/`remove` lessons from the first installs (2026-11-02): `remove` deletes the install folder at once unless it runs from inside it (a delayed `rd` once wiped the files a `setup` run straight afterwards had copied, so the service couldn't load its helper DLL); `setup` waits for the old service process to exit and retries each copy briefly (Windows reports "Stopped" a moment before the process is gone, so copying over the exe failed with "in use").
  - Control pipe `HapticLink` (SYSTEM, Admins, Interactive): `HELLO <app>` → `OK <version> 1` (`HELLO PeripheralHub` adds the client exe from `GetNamedPipeClientProcessId` to the readers and HidHide's allowed list), `STATUS` → `OK state|enabled|haptics|mac|message`, `ENABLE`/`DISABLE`, `FEATURES` → `OK speaker=0|1`, `SET speaker 0|1` (both since service 1.1.0), `RECHECK` (since 1.2.3: look for the requirements now), `ATTACH` (since service 1.2.0: the tray holds this connection open while it runs; with none for 5 s the bridge stops and STATUS says state `closed`, owner 2026-11-02: "HapticLink should stop completely when the tray is not running"; PeripheralHub treats `closed` as not running and hides its switch; new commands are additive and keep protocol 1; **STATUS must keep exactly five fields**: the tray and PeripheralHub split it with a limit of 5, so a sixth would end up in the message). Protocol changes must stay compatible or bump the protocol number: PeripheralHub ships on its own schedule. STATUS's haptics flag follows `HapticsRelay.Recording` (since service 1.0.1; before, it only meant the speaker was shown and once said 1 while capture kept failing). The service loop re-checks it every second: "starting haptics" for the first 10 s, then "On without haptics: <reason>. Retrying…" until recording works; the tray shows "on (no haptics)".
- The app is two exes in one folder (split 2026-11-03, owner: the tray "should not take any resources; all work is being done by the service anyway"); `src/HapticLink.Shared` (pipe client, `ServiceSetup`, `DoubleInput`, log, Run key, icons in `Assets`) is compiled into both.
  - `src/HapticLink.Tray` → `HapticLink.exe`, always running: **Native AOT, plain Win32, no WinForms** (hidden window + `Shell_NotifyIconW` + `TrackPopupMenuEx`, re-adds the icon on `TaskbarCreated`, dark menus via uxtheme ordinals 135/136). ~5 MB in Task Manager, flat (the WinForms tray was ~14, ~20 after hours); it calls `GC.Collect()` once a minute, since poll garbage otherwise grew it ~0.35 MB/min and Native AOT ignores `System.GC.Gen0Size` in the exe (`DOTNET_GCgen0size` only as an environment variable). Velopack 1.2.161 hooks and updates (keep in step with `.config/dotnet-tools.json`; Velopack works under AOT). **The update check runs in a short-lived copy, `HapticLink.exe --check-updates`** (exit 10 + version on stdout = downloaded, 0 = up to date; auto-apply off so it never applies under the running tray): in the tray itself the HTTP/TLS code it loads stayed and kept it at ~10–11 MB. *Restart to update* exits and starts `HapticLink.exe --restart`, which waits up to 10 s for the single-copy mutex while Velopack applies the downloaded update on startup. Tested 2026-11-06 with local packages (`build-installer.ps1` takes test versions like `1.2.4-test.1`, below 1.2.4 for Velopack): 1.2.3 → new layout, Check for updates against GitHub ("Up to date"), and Restart to update with a package placed in `%LOCALAPPDATA%\HapticLink\packages`. Source: `GithubSource(https://github.com/hemanthvj12/haptic-link)`. State lives on the window thread; pipe calls run on the pool and post back. Icons are `app.ico` (on) and `tray-off.ico`, embedded. Menu items have no hover tooltips (Win32 menus can't). **Publishing needs the MSVC linker, and .NET 8's ILCompiler only looks for Visual Studio 2019/2022**: with VS 2026 the publish runs inside `vcvars64.bat` with `-p:IlcUseEnvironmentalTools=true` (`build-installer.ps1` does this). The AOT exe carries its own copy of the runtime, so runtime security fixes need a rebuild with a current .NET 8 SDK.
  - `src/HapticLink.Setup` → `HapticLink.Setup.exe` (WinForms): `SetupWindow` only, started by the tray when it's needed (`--required` before set-up or with a newer bundled service, `--why <reason>` for "Needs setup"/double input, no argument from the menu) and exiting when closed; exit code 0 = completed. The tray exits after a cancelled setup while no service runs. It runs `service\HapticLink.Service.exe setup --progress <file>` elevated (see "Setup window"). Icon drawn in code (`IconMaker`; `HapticLink.Setup.exe --write-icon <path> [idle]` regenerates `app.ico` / `tray-off.ico`).
  - Uninstall runs `remove`. Data in `%APPDATA%\HapticLink` (logs, both exes write `app.log`).

## Protocol facts (verified on the owner's DualSense, 2026-11-01)
- **Bluetooth output** `0x31` (78 bytes): `31, seq<<4, 10`, the 47-byte body of USB `0x02`, CRC32 at 74..77. CRC = zlib CRC-32 over `A2` + report (seeded state `~0xEADA2D49`). Windows pads output writes to `OutputReportByteLength` (547) and the pad accepts that; `HidD_SetOutputReport` at the exact size fails with 87.
- **Haptics** `0x32`, **142 bytes** (141 data + id; 141 put the CRC a byte early and nothing played): `32 00 | 91 07 FE 00 00 00 00 FF <counter> | 92 40 <64 s8, L/R interleaved, 3 kHz> | zeros | CRC`.
- The light bar ignores colours until a release: `valid_flag2 0x02` + `lightbar_setup 0x02` (USB bytes 39/42).
- Input: BT `0x31` → USB `0x01` = same fields one byte earlier. Windows pads basic `0x01` BT reports to full length: don't forward them.
- **Haptics relay** (owner: "waaaay better" after these): WASAPI loopback of the pad speaker (4 ch / 48 kHz float), ch 3-4 → 96-tap Hann-sinc low-pass 1.2 kHz → ÷16 → s8; one `0x32` per 10.667 ms on a high-resolution waitable timer (bursts felt late); **silent blocks are sent while the game's stream is open** (gating made the pad swallow short effects: Stellar Blade's menu clicks came through every 3rd–4th time); queue ≤ 2, trimmed to 1 when full for long (a limit of 1 dropped ~8%). **Capture must retry**: right after the endpoint appears `GetService` can fail with 0x88890004.
- **Latency (measured 2026-11-02, test pulses on the owner's pad):** Steam's speaker runs the engine at 10 ms only (`IAudioClient3` shared period 10–10), so loopback hands over 480-frame chunks and a shorter period is impossible. A report holds 10.67 ms, so blocks arrive in a 0–10 ms sawtooth against a steady clock; ~5 ms average wait is the floor for a steady clock. The old free-running clock averaged 11.0 ms queue wait; the clock that follows the blocks (window 48, margin 1.5 ms, late blocks sent on arrival) averages 6.4 ms, ~4 late and ~0 dropped per 2,800 reports. HID writes take 0.6 ms (max ~1.8). The endpoint's loopback timestamps run ~13–17 ms ahead of when we write, so "mix to write" in the log is negative: a relative measure only. What's left is the game's buffer, Bluetooth and the pad. Every 30 s of haptics the log gets a "haptics timing" line.
  - **Our code is at its practical limit (owner agreed, 2026-11-02).** Rumble/triggers: `PumpOutputs` polls every 1 ms and writes straight away (~1 ms). Rejected for haptics: sending blocks as they arrive instead of on a steady clock (~5 ms more, but uneven delivery is what felt late and uneven in the first version) and trimming the filter or margin (1–2 ms, below Bluetooth's own jitter, risks dropped blocks). DSX feels the same or worse, which fits the rest being outside any app. Remaining gains are hardware: Wi-Fi off 2.4 GHz (combo cards share the radio), no Bluetooth audio at the same time, an adapter with line of sight; or a USB cable.
- **Speaker sound over Bluetooth** (works on the owner's pad, 2026-11-02: a test tone, then Stellar Blade's parry sound with its controller-speaker setting on; not yet tried with headphones): report `0x36`, 398 bytes, after LinuxAudio4Dualsense5 / DS5_Bridge: `36 seq<<4 | 91 07 FE 40 40 40 40 40 <counter> | 90 3F <63-byte state> | 92 40 <64 haptics s8> | 93 C8 <200 bytes Opus> | zeros | CRC at 394`. `0x96` instead of `0x93` = headphone jack (chosen by the plug flag, USB input byte 54 bit 0). Opus via Concentus (managed only: `AttemptToUseNativeLibrary = false`), 48 kHz stereo, 480-frame (10 ms) frames, CBR 160 kbit/s = exactly 200 bytes, complexity 0. Each 512-frame block (the same 10.67 ms as a haptics report) is resampled linearly to 480 frames. The state sub-packet has the USB 0x02 body layout; we set only the audio valid flags (0xB0, 0x80: volumes, `audio_control`, `audio_control2`) with the game's last values or speaker 0x64 / headphones 0x7F / path 0x30 (speaker) or 0x00 / preamp 0x02, so rumble, triggers and lights aren't touched. `HapticsRelay` sends 0x36 instead of 0x32 from a stream's first speaker sound (channels 1-2 above about -66 dB, 40 ms fade-in) until the stream closes; the built-in speaker is mono (the channel with sound, or both mixed), headphones stereo. Windows pads every write to 547 bytes anyway, so 0x36 costs no extra airtime. Log: "speaker: playing (…)" / "speaker: stopped", and the timing line counts reports with speaker sound. `dotnet`-built scratch test that renders a tone to the endpoint id is the quickest check.
- **Microphone (not released; work on branch `mic-wip`, 2026-11-02).** Steam's *Streaming Microphone* driver is a loopback (render side → capture side), so a second ROOT\MEDIA devnode (marker `HapticLinkMicIndex`) gives a recording device, as punktfunk's minted microphone does; both sides must run 2 ch 48 kHz. Audio mask `0xFF` (bit 0) in the 0x32/0x36 config makes the pad stream its mic as extra input reports `0x31`: byte 1 low nibble **2** (input reports have 1), byte 2 a frame counter, Opus from byte 3 (TOC `0xD4`, CELT 10 ms mono 48 kHz) to the CRC, 100 frames/s; they decoded fine with Concentus. The pad only streams while those reports keep asking, so with no game sound silent 0x32 reports must keep going. Open problems: **lots of background noise** (echo/noise cancel bits 0x0C in `audio_control` added on the branch, untested), and **anything else reading the real pad must skip mic frames**: PeripheralHub's battery flickered (100 % / charging) while the mic ran.
- **Speaker:** a ROOT\MEDIA devnode (marker `HapticLinkPadIndex` in Device Parameters) with hwid `ROOT\SteamStreamingSpeakers`, created with `SetupDiRegisterDeviceInfo` (DIF_REGISTERDEVICE fails from a service), bound to Steam's installed INF (found from a devnode using it or by scanning `oem*.inf`). **When it isn't in the driver store** (Steam installed, Remote Play never used), `SteamSpeakerDriver` (service 1.2.3) unpacks `drivers/Windows10/x64/SteamStreamingSpeakers.inf/.sys` + `steamstreamingspeakers.cat` from Steam's `bin\drivers.exe` ("Steam Drivers Archive", signed by Valve: a zip written as a stream, data descriptors and no central directory, so entries are found by local headers and inflated to the end of their deflate stream) and runs `pnputil /add-driver`; checked 2026-11-02: byte-identical to the driver store copy; tested by deleting the package (`pnputil /delete-driver /uninstall`) and rerunning setup: added back in ~0.4 s and bound to every devnode with that id. **Uninstalling the driver package wipes our devnode's Device Parameters (the marker)**, so the instance id is also kept in `HKLM\SOFTWARE\HapticLink\SpeakerDevnode` and `Readopt` re-marks it (opened without a class filter); before that a new devnode was made and the old one stayed as a visible plain "Speakers". Binding the driver again also gives every other devnode with that id (Steam's, punktfunk's) a fresh, visible endpoint, and Windows made one of them the default output: `Ensure` takes the default before anything and `Audio.RestoreDefault` puts it back whoever took it. We never ship Valve's driver; without Steam, STATUS says "Steam isn't installed…" and the tray shows *Set up HapticLink…*, whose window links to Steam. Stamped through `IPropertyStore` (helpers shared in `AudioDevices`): description "DualSense Controller (HapticLink)" / device name "Steam Streaming Speakers" (both the owner's choice, 2026-11-02: was "Wireless Controller", the real pad's name; the device name is Steam's own and is stamped only because an earlier build had overwritten it; with no "Wireless Controller" anywhere in the name Stellar Blade's haptics and speaker still work, so it finds the pad's speaker by the container id). **Sound settings' second line comes from the endpoint's own device `SWD\MMDEVAPI\<endpoint id>`, whose description Windows sets once and never refreshes** (not on audio service or device restarts): after the rename it still said "Wireless Controller (4- DualSense Wireless Controller)" while its friendly name was right, so `Devnodes.SyncDescription` copies the friendly name into it after stamping (fixes upgrades from 1.0.x), the container id, 4 ch 48 kHz formats. Hidden with `IPolicyConfig::SetEndpointVisibility` when idle; showing it can make it the default output, so `KeepDefault` puts the old one back. **A freshly made endpoint can refuse loopback recording of its own mix format** (AUDCLNT_E_UNSUPPORTED_FORMAT, 0x88890008, seen 2026-11-02 right after the split: the stamped 4-channel format was served by `GetMixFormat`, but the audio engine still ran the driver's old one, from a user process too, so not a service/session-0 issue). `IPolicyConfig::SetDeviceFormat` with the same formats (what Sound settings does) makes the engine apply it at once, and it persists; `Audio.EnsureFormat` does that whenever showing the speaker finds recording refused. Each new devnode gets a new endpoint GUID; a removed devnode's endpoint lingers as DeviceState "not present" (0x4) and a new devnode can reuse the instance id, so `FindEndpoint` skips not-present endpoints (matching one once skipped binding Steam's driver: no endpoint, no haptics). **Don't disable the speaker devnode to test**: while it's recorded, `pnputil /disable-device` only schedules the disable for the next reboot and `/enable-device` then refuses; undo by freeing it (DISABLE), `pnputil /remove-device`, restarting the service. To test haptics failing, stop `Audiosrv` (0x88890010 while it's down; recording comes back by itself within a second of starting it).
- **HidHide is required for triggers to feel right**: without hiding, games drive both pads.
- **HidHide only blocks new opens** (GitHub issue #1, 2026-11-02: a user with HidHide saw two pads in a gamepad tester, the real one frozen because the bridge switches it to 0x31 reports). Windows' game controller input opens the pad as it connects, so hiding it afterwards changes nothing for browsers and most games. Since service 1.2.1 `Bridge.HideRealPad` hides *before* opening the pad (so the service is allowed even when DSX hid it), and when the visibility changed (newly listed, cloak was off, inverse mode was on) or HidHide's filter isn't in the HID node's `DEVPKEY_Device_Stack` (HidHide installed while connected), restarts the node (`DeviceNode.Restart`: `CM_Disable_DevNode` non-persistent + `CM_Enable_DevNode`), waits for it, then checks the stack again. `Restore` restarts it again so games see it once unhidden. A failed hide (restart refused, filter still not attached) is double input (below), not a warning any more. The owner's PC never showed it because DSX had listed the pad long before. Inverse mode (`--inv-on`: the app list becomes a block list) is turned off for the session.
- **Setup window (1.2.3; owner, 2026-11-02: "our app doesn't need to install hidhide itself"):** `SetupWindow` first checks the two apps HapticLink needs without admin rights (`Requirements`: HidHide by its registry path/CLI, Steam by `steam.exe` plus either `bin\drivers.exe` or Steam's speaker INF in `C:\Windows\INF`), each a green tick or a red cross with a "Get …" link; with either missing the buttons are *Check again* and *Exit setup* (exiting while no service runs exits the app; it comes back at the next start). With both there, *Install* runs setup elevated, which appends `step|state|message` lines (steps `driver`, `hidhide`, `speaker`, `service`; states `run`/`ok`/`fail`/`skip`) to a temp file the window polls every 150 ms, since a ShellExecute'd elevated process can't return output. Setup's HidHide step registers the service exe (`--app-reg`) and checks `--cloak-state` answers; the speaker step adds Steam's driver from Steam's files when it isn't in the store. `HapticLink.exe --setup` (or `HapticLink.Setup.exe` itself) opens the window alone (works beside the running tray). Light/dark follows `AppsUseLightTheme`, dark title bar via `DWMWA_USE_IMMERSIVE_DARK_MODE`, layout in code per DPI. The tray's *Set up HapticLink…* shows while setup is needed or STATUS says HidHide/Steam isn't installed. 1.2.2's HidHide download-and-install (`--install-hidhide`, `HidHideInstaller`) was removed. **Requirements gone later** (owner: "it should refuse to turn on and provide the same setup screen"): every 5 s and before bridging, the loop checks `HidHide.FindCli()` and `SpeakerEndpoint.MissingDriver` (set when Steam's driver is missing and couldn't be added; `Recheck` retries every 15 s, notices the driver vanishing after set-up, and `RECHECK` forces it). Either missing → the bridge stops and STATUS is `error` with "Needs setup: <what>. Open HapticLink's setup to fix it." (state `starting` "Checking HapticLink's setup…" while the first check runs). The tray opens `SetupWindow` with the reason once per occurrence (`whyOff` mode: no Install section; with both ticks it says HapticLink turns back on and finishes with Done, no reinstall). Tested 2026-11-02 with HidHide uninstalled. **Double input** (owner, 2026-11-02, after 1.2.2 didn't fix his friend's two controllers; like DSX's "Fix double input" but inside "Needs setup"): (1) the tray, while state is `on` for over 5 s, checks Windows' raw input device list (`DoubleInput.RealPadVisible`: any `HID#{00001124…}_VID&0002054C_PID&0CE6/0DF2` device) and sends `DOUBLE-INPUT` once per "on" stretch; verified on the owner's PC that the real pad is in that list with HapticLink off and absent with it on, so it is exactly what gamepad testers see; (2) the service runs `HidHideControl.Check` every 10 s while bridging (cloak on, pad listed, service exe allowed, inverse off, filter in the stack); (3) a failed hide at bridge start (`Bridge.HidHideProblem`). Any of them sets `_hidHideBroken`: the bridge stops (its restore unhides and restarts the pad, so only the real pad is left) and STATUS says "Needs setup: HidHide isn't hiding the controller: <what>. …" until `REPAIR`, which clears it and starts the bridge with `forceRestart` (the pad is restarted even if HidHide's settings were already right). The window shows HapticLink's rows with their state (driver/service ticked, *HidHide set-up* crossed with the reason), Repair waits for `on`, gives Windows 3 s, then checks the raw input list itself; with no controller connected (`waiting`) the repair counts as done. Tested by turning cloaking off mid-session: caught within 10 s, bridge stopped, window opened. Uninstall leaves HidHide and Steam's speaker driver (shared with DSX, DS4Windows, Steam, punktfunk); it removes HapticLink's own driver package, service, speaker devnode, certificates and folder.
- COM: create objects via `ComObjects.Create` and cast to interfaces; two `[ComImport]` classes for the MMDevice enumerator clash ("Unable to cast 'MMDeviceEnumerator' to 'MMDeviceEnumerator'").
- A Bluetooth pad once showed "Driver error" (code 10) and had to be re-paired; cause unproven (half-asleep pad with the bridge holding handles). The bridge now lets go after 3 s of silence and refuses to start when the feature reads fail. **"Couldn't start: the controller didn't answer"** (STATUS `error`, retried every 15 s) is that refusal: on 2026-11-06 the connected pad timed out on feature 0x05 even from a plain `HidD_GetFeature` outside HapticLink (error 121); turning the controller off (hold PS ~10 s) and on fixed it, and the bridge came up within seconds. Seen 7 times since 2026-11-03, and again 2026-11-07 right after swapping the service exe. **Pattern (unproven):** both 2026-11-06 (switch off and on within 2 s) and 2026-11-07 (service restart) came after two controller restarts a few seconds apart: the bridge's `Restore` restarts the node to un-hide it, then the next start restarts it again to hide it. Once stuck, every retry restarts it twice more and it never recovers by itself. Ideas if it keeps happening: skip the hide-restart when the pad was restarted moments ago, wait longer after a restart before reading 0x05, or back off further after repeated failures.

## With PeripheralHub
- PeripheralHub reads the real pad's battery and, since its 1.3.0, its paired devices (feature 0x0B, one per PS + △ ○ ✕ □; layout in PeripheralHub's CLAUDE.md), allowed through HidHide via `HELLO PeripheralHub`. It shows the waves on the real pad's tile, hides the virtual pad (origin `HLINK_PAD`), and its menu switch sends ENABLE/DISABLE. Future DualSense controls (mic/speaker mute over Bluetooth) go through this pipe; on a cable PeripheralHub can use Windows audio itself.

## Working from this session
- Commands run inside the Claude desktop app's MSIX sandbox (AppData writes are redirected); start exes through Explorer (`Start-Process explorer.exe -ArgumentList '"<path>"'`) to run them outside it. UAC (`runas`) children run outside too.
- Installs: Setup installs per user to `%LOCALAPPDATA%\HapticLink` (start it through Explorer from here); the service goes to `%ProgramFiles%\HapticLink\Service`. Development builds of the service are tried with `setup` from `artifacts\service` elevated, never by installing a local Setup. To go from a development install back to a release: exit the dev tray app, run `artifacts\service\HapticLink.Service.exe remove` elevated (from that copy, not the installed one, so the folder goes at once), then run the release's Setup.
- Talking to the pipe from a throwaway PowerShell (`NamedPipeClientStream`, one line, read one line back) works from this session: handy for STATUS and for ENABLE/DISABLE to restart the bridge.
